# 日本語スタイルルール

記事の日本語を書く・直す・チェックするときの具体ルール集。考え方の原則は `AGENTS.md`、筆者の文体は `.claude/skills/tone-check.md` にあり、このファイルはその間を埋める「どう書くか／何を直すか」の実務ルールを置く。

## 優先順位

ルール同士がぶつかったら、上を優先する。

1. **技術的な正確さ**（`fact-check` で確認する事実）
2. **筆者が自分で指定した文面**。ルールに反していても書き換えない。直したほうがよいと思ったら提案に留める
3. **筆者の文体**（`tone-check.md`）。「！」「w」「。。」「〜と思います」「（本当に助かる）」のような括弧内コメントは筆者の声なので、このファイルのルールで消さない
4. **このファイルのルール**
5. 一般的な文章術

各ルールには「どこに当てるか」と「例外」を書く。例外のないルールを機械的に全置換すると、正しい文まで壊れるため。

## 1. 読者と目的

- 書き始める前に「想定読者」「読み終わったらできること（ゴール）」「なぜこの記事を書くのか」を決める。決まらないうちは本文を書かない（`draft-sparring` スキルで壁打ちする）
- 冒頭の数段落で、関係ない読者が離脱できるようにする。対象のサービス・前提知識・対象バージョンを早めに書く
- 読者に何かしてほしい記事（イベント告知、移行手順など）は「誰が、いつまでに、何をするか」を冒頭に書く
- 1 ページで説明できることを水増ししない。短い記事でよい

## 2. 構成

- **大枠から細部へ**。全体像や前提を先に書き、補足や派生は後ろに回す
- **既知から未知へ**。読者が知っていることから始め、新しい用語・概念はその上に積む。用語は「現象を説明してから名前を付ける」順にする
- 1 段落 1 トピック。2 つのことを書いていたら段落を分ける
- 箇条書きや選択肢は 7 項目以内。超えるときは階層化する
- 見出しは「その節に何が書いてあるか」が分かる名札にする。結論を先に明かす見出し、広告コピー風の見出し、「〜だけ」「〜してくれる」の同じ形の連続、見出し内の読点・コロン・括弧で役割を足す書き方は避ける
  - 例外: 筆者の記事でよく使う `# はじめに` `# まとめ` `# 最後に` はそのまま使う
- 失敗談は「何が起きたか → なぜそう判断したか → 何が原因だったか → 読者が再利用できる確認方法」の順にする。「転機が訪れた」「そこで初めて気づいた」のような認識の変化の物語で水増ししない
  - 筆者の自己開示（ハマった・苦しかった）は残す。削るのは情報を増やさない演出だけ

## 3. 文と段落

- 一文は一口で食べられる長さにする。「〜ですが」「〜ので」「〜し」「〜して」「〜ため」が続いて長くなったら、そこで文を切る。目安は 100 字以内。声に出して一息で読めなければ長い
- 1 段落はおおむね 300 字以内。超えたら話題の切れ目で分ける（文言は変えずに空行を入れるだけでよい）
- 強調のためだけに 1 文ずつ空行で区切らない（いわゆる改行型）。意味のまとまりは段落で示す
- 接続詞は既にある論理関係を示すもの。理由が書かれていない 2 文の間に「しかし」を足しても説明にはならない。理由そのものを書く
- 主語を固定する。「私」は筆者 1 人に固定し、AI の提案・実行結果は「Claude Code が〜した」のように主語を明示する
- 無生物主語（「この制約が設計を導いた」「コードが語る」）は、A から B に至る説明を省いていないかを確認する。因果関係そのものを述べているだけなら残してよい

## 4. 語彙

### 4.1 意味の広い言葉は具体的な言葉にする

AI がよく使う「意味は何となく分かるが、読者が補わないといけない言葉」は、文脈に合わせて言い換える。一律削除はしない。

| 言葉 | 言い換えの方向 |
|------|--------------|
| 静かに（静かに壊れる、等） | 徐々に、気づかないうちに、エラーを出さずに |
| 刺さる | 共感した、納得した、耳が痛かった |
| 効く／効いてくる | 効果がある、改善する、減らす、（何が・どう変わるかを書く） |
| 壊れる（運用が壊れる、等） | 停止する、整合性が崩れる、機能しなくなる |
| 溶ける（ルールが溶ける、等） | 曖昧になる、形骸化する |
| 育てる（台帳を育てる、等） | 整備する、追記していく、精度を上げる |
| 腐る（仕組みが腐る、等） | 古くなる、更新されなくなる |
| 持ち帰る（学びを持ち帰る） | 学べる、身に付く、自分の環境で試せる |
| 正体（〜の正体） | 原因、中身、実体 |
| 仕込む | 設定する、入れておく |
| 手が止まる | 作業が止まる、（誰が何をできなくなったかを書く） |

### 4.2 定着していない言葉の組み合わせを作らない

「事故を踏む」「穴を踏む」「種が割れる（原因が分かる意味で）」「一文に落ちる」「API 契約（API contract の直訳）」のように、日本語話者が使わない組み合わせは避ける。迷ったら検索して用例があるか確かめる。

### 4.3 用語

- 独自の呼び名を作るなら「ここでは〜を○○と呼びます」と定義してから使う。既存の専門用語と独自の呼び名を同じ調子で並べない
- 想定読者が知らない専門用語は初出で説明する。記事の後ろで説明していても、前で使った時点では読者は知らない
- 比喩は「何と何が対応しているか」が迷わず分かるときだけ使う。単語 1 つだけ比喩に置き換える（「設定ミスがある家」）のは避ける
- 「その前提」「この構造」「この仕組み」と書いたら、指している内容が直前に書いてあるか確認する

## 5. 演出（AI っぽさ）を避ける

「AI っぽいから消す」のではなく「読者に余計な推測をさせるから直す」。直した結果 AI っぽさが残っても構わない。

| 種類 | 例 | 直し方 |
|------|----|-------|
| ダッシュ | 「〜ではない——〜だ」 | 「ではなく」「なぜなら」など関係を表す言葉か、読点・句点にする |
| 決め台詞 | 「これが〜の正体です」「要するに、答えはあるが解き方がない。」 | 普通の説明文にする。どうしても残すなら 1 記事 2 回まで |
| 誇張 | 「致命的」「劇的に」「重大」「これがいちばん怖い」 | 実際の影響（何が・どれだけ）を書く |
| 中身のない対比 | 「〜は単なる A ではない。B だ」「A でも B でもなく C だ」 | A・B が読者の誤解を実際に正すときだけ使う。そうでなければ C だけ書く |
| 宣言 | 「結論から言うと」「正直に言うと」「ここが重要です」 | 宣言を消して、重要な理由を本文で書く |
| 読者の決めつけ | 「CI が通ると人は安心します。でも〜」「あるあるですよね」 | 読者がどこで困るかを説明する |
| まとめ癖 | 段落末の「〜と考えると整理しやすくなります」「目的に合った選択が重要です」 | 削る。具体的な結論が直前にあるなら一般論で包み直さない |
| 予告だけ | 「これが後で効いてきます」 | その場で関係を書くか「理由は○○の節で説明します」と参照先を書く |
| 名付け | 「本書では〜と呼びます」を連発 | 普通に言えば伝わるなら名前を付けない |
| 予防線の過多 | 「〜ことがある」「必ずしも〜ではない」の連続 | 確認済みの事実は断定する。例外は主張に関係するときだけ書く |

筆者の文体との関係: 所感・感想の「〜と思います」「〜と感じています」は筆者の声なので残す。直すのは事実や仕様を述べる文まで弱めてしまっている箇所だけ。

## 6. 書式

- 太字は拾い読みに必要な箇所だけ。1 段落に何個も入れない
- 引用ブロック（`>`）は出典のある引用に使う。心の声や要点の強調には `:::message` を使う
- 箇条書きの種類を区別する。並列は箇条書き、手順は番号付き、比較は表、完了確認はチェックリスト。行動指針をチェックリストの形にしない
- 文中の並列はナカグロ（・）ではなく読点（、）で書く。箇条書きにしたときに崩れるため
  - 例外: 「Q&A」「AWS・Azure・GCP」のように固有の表記として定着しているもの
- リンクテキストを「こちら」にしない。「詳しくは [Amazon CloudWatch のドキュメント](...) を参照してください」のようにリンク先の名前を書く
  - 例外: 筆者がよく使う、connpass や Speaker Deck の URL を単独行で貼るスタイルはそのまま
- 見出しに絵文字（📌 など）を付けない（`tone-check.md` と同じ）

## 7. 技術記事に特有のルール

- **正式名称**: 製品名・サービス名は公式の表記をコピーして使う（GitHub、JavaScript、Visual Studio Code、Amazon CloudWatch など）。略称は初出で正式名称を書いてから使う。読みにくいものは読み方を添える
- **時点とバージョン**: 「今年の」「先日の」ではなく「2026 年 11 月 21 日」と書く。対象バージョン、リージョン、検証日を書く
- **例示用の値**: 例の IP アドレスは `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`（RFC 5737）、ドメインは `example.com` などの例示用ドメイン（RFC 2606）を使う。アカウント ID も `123456789012` のようなダミーにする
- **数字**: 数字を出すなら「何のための数字か」「母数・期間・条件」を添える。意図のない数字を並べて具体的に見せない
- **表記の使い分け**: リンクは「張る」（ページ間をつなぐ）、URL は「貼る」（チャット等に貼り付ける）。例示の略は「ex.」ではなく「e.g.」
- **体験は捏造しない**: 実際にやったこと、出たエラー、かかった時間は、筆者の素材（`drafts/` のダンプや会話）に根拠があるものだけ書く。足りなければ筆者に聞く

## 8. ルールの育て方

- 赤入れを 1 件受けたら、その 1 か所を直すだけで終わらせない。
  1. ほかの箇所にも当てはまるルールに書き直してこのファイルに足す（どこに当てるか・例外も書く）
  2. 記事全体から同じパターンを検索して直す
  3. `feedback-log.md` に日付・元の指摘・追加したルールを記録する
  4. 字面だけで判定できるものは `ng-words.json` に足して自動チェックにする
- 強めすぎたルールは緩める。全置換で文章が単調になったら「機械的に全置換しない」と例外を書く
- 自動チェックに入れるのは「一度指摘して、字面だけで判定できる言葉」に絞る。機械で判断できないルールは人間と AI のレビューに残す
