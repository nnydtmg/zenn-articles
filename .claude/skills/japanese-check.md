# 日本語チェック スキル

記事の日本語を、読者が意味や理由を補わずに読めるかという観点でチェックする。
「AI っぽい言葉を消す」ことが目的ではない。読者に余計な推測をさせる箇所を直すのが目的で、直した結果 AI っぽさが残っても構わない。

役割分担:

- 技術的に正しいか → `fact-check`
- 筆者の文体に合っているか → `tone-check`
- **日本語として読者に伝わるか → このスキル**

## 参照するファイル

チェックの前に必ず読む。

1. `AGENTS.md`（原則と公開前チェックリスト）
2. `.claude/writing/style-rules.md`（具体ルール、優先順位、例外）
3. `.claude/writing/feedback-log.md`（過去の赤入れ。同じ指摘を繰り返さないため）
4. `.claude/skills/tone-check.md` の「筆者の文体プロファイル」（筆者の声を壊さないため）

## 実行手順

### 1. 対象を決める

ユーザーがファイルを指定していなければ、直近の会話で話題になっている記事を対象にする。分からなければ聞く。

### 2. 自動チェックを走らせる

```bash
node scripts/check-writing.mjs <file>
```

結果は「機械が字面で拾った候補」として扱う。誤検知（固有の表記のナカグロ、引用の中の言葉、筆者が意図して使った言葉など）は指摘から外す。

### 3. 全文を通して読む

章ごとに分けず、記事全体を 1 回で通して読む。分割すると、章をまたいだ重複や用語の揺れが見えなくなるため。
次の順に確認する（AGENTS.md の「公開前レビュー」と同じ順）。

1. **問いと答え**: 冒頭で示した問い（「〜を試してみました」の結果どうだったか）に、本文が答えているか
2. **説明順序**: 大枠から細部、既知から未知になっているか。用語が説明より前に出ていないか
3. **論理**: 2 文の間の理由が抜けていないか。「その前提」「この構造」の指す内容が書いてあるか
4. **根拠**: 体験・数値・仕様に根拠があるか。数字に目的と条件が添えられているか
5. **表現**: 語彙、演出、書式（style-rules.md の 4〜7 章）

### 4. 重要度をつけて報告する

指摘は 3 段階に分ける。全部を直さなくても公開できるように、筆者が対応範囲を選べるようにするため。

- **MUST FIX**: 誤解を生む、論理が成り立たない、事実や体験の捏造が疑われる
- **Nice-to-have**: 直すと読みやすくなる
- **Nitpicking**: 好みの範囲、直さなくてもよい

レビュアーとしての注意:

- 指摘をひねり出さない。問題が少なければ「少なかった」と書く
- 重箱の隅（文脈から明らかな曖昧さ、主張に関係ない例外の欠如）を MUST FIX にしない
- 「分かりにくい」だけで終わらせず、どう直すかを修正案で示す
- 良かった箇所も書く。筆者が次も同じ書き方を選べるようにするため

出力フォーマット:

```
## 日本語チェック結果: <ファイル名>

### サマリ
<全体の評価（1〜2 文）>
- MUST FIX: X 件 / Nice-to-have: Y 件 / Nitpicking: Z 件
- 自動チェック: N 件中 M 件を採用（残りは誤検知として除外）

### MUST FIX
**[1] L42** <ルール名（style-rules.md の節番号）>
- 現在: 「<該当箇所を段落ごと引用>」
- 読者が困る点: <何をどう誤解・推測させるか>
- 修正案: 「<段落全体の修正後>」

### Nice-to-have
（同じ形式）

### Nitpicking
（箇条書きで簡潔に）

### 良かった点
- <維持してほしい書き方>
```

修正案は、変えた文だけでなく段落全体を示す。文の良し悪しは前後とのつながりで決まるため。

### 5. 修正する場合は二段階で進める

1. 上の報告（修正案）を出した時点では、記事ファイルを書き換えない
2. ユーザーが「反映して」「MUST FIX だけ直して」などと言ったら、その範囲だけを Edit で反映する

反映時の注意:

- 指摘された箇所だけを直す。周りの段落まで気を利かせて書き直さない
- 筆者が自分で指定した文面は、ルールに反していても書き換えない
- 筆者の文体（「！」「w」「。。」「〜と思います」）を消さない
- 技術的な事実、数値、断定の強さを変えない。変えざるを得ないときは理由を添えて確認する
- 反映後にもう一度 `node scripts/check-writing.mjs <file>` を走らせ、新しい指摘を増やしていないか確かめる

### 6. 指摘をルールに還元する

ユーザーから赤入れ（「ここ AI っぽい」「この言い方は私っぽくない」など）を受けたら、`style-rules.md` の「8. ルールの育て方」に従う。

1. 言葉にならない違和感は、似た箇所を並べて共通点を言葉にし、ルールの文にする
2. ルールに「どこに当てるか」と「例外」を書いて `style-rules.md` に足す
3. 記事全体から同じパターンを探して直す（修正案として出し、反映は二段階で）
4. `feedback-log.md` に記録する
5. 字面で判定できるものは `ng-words.json` に足す。「これ NG ワード」と言われたら必ず足す

## 注意事項

- 引用ブロックの中、コードブロックの中、他者の発言の引用は、表現のチェック対象外
- ルール同士がぶつかったときは `style-rules.md` の優先順位に従う
- 迷う言い回しは 1 つに決め打ちせず、番号付きで複数案を並べて筆者に選んでもらう
